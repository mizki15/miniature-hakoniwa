## 1. コンセプト

**「机の上に置いた小さな自然を、ずっと眺めていられる」**

- ブラウザだけで動く、自然豊かなボクセルの箱庭（ジオラマ）
- 主役は**眺めること**。水がきらめき、木々が揺れ、昼夜と季節が巡る
- プレイヤーは「神の手」として少しだけ干渉できる（畑を耕す、木を植える、水路を引く 等）
- **放置で育つ**：閉じている間も時間が進み、戻ると畑が実り、森が広がっている
- サーバー不要。処理も保存もクライアント側＋ユーザー自身のクラウドストレージ

### ターゲット
- 癒やし系・放置系ゲームが好きな層、作業用BGM／壁紙的に画面を開いておきたい層
- PCブラウザで遊ぶ。スマホ・タブレットは**閲覧限定**（PC で育てた箱庭をクラウド同期で外出先から眺める）

### 体験の柱
| 柱 | 内容 |
|---|---|
| 眺める | 斜め上からの見下ろし、自由回転・ズーム、ミニチュア感のある被写界深度（ティルトシフト） |
| 育つ | 実時間ベースの成長（作物・樹木・動物・水の流れによる地形変化） |
| 触る | 小さな干渉で箱庭が変化する。干渉しなくても成立する |
| 残る | 自分の箱庭がクラウドに保存され、どの端末からでも続きを見られる |

## 2. ゲームデザイン

### 2.1 箱庭の構成（初期案・テストプレイで調整）
- サイズ：**64×64×32 ボクセル**から開始 → 128×128×48 まで検証
  - チャンク単位（16×16×16 または 32×32×32）で管理し、拡張可能にする
- 地形：シード値から手続き生成（丘・川・池・小さな滝・森・草原）
- 境界：台座付きのジオラマ風（地層の断面が見える）にすると「箱庭感」が強く出る

### 2.1.1 見た目（ボクセル表現）
- 基本は**純粋な立方体**。形状（ジオメトリ）は常に立方体のまま保つ
- 「角丸」はシェーダー側で表現する案を検証する
  - 面の端に向かって法線を少し傾け、縁にハイライトと AO を乗せる → 形は立方体のまま柔らかく見える
  - 低コストで設定から ON/OFF 切替できる。不十分なら角を面取りしたメッシュ生成を別途検討
- 最初の技術検証で両方を並べて比較し、どちらを標準にするか決める

### 2.2 時間とシミュレーション
- **昼夜は現実時刻と連動**：プレイヤーの端末時刻で、朝に開けば箱庭も朝、夜に開けば夜
  - 夜しか遊べない人のために「表示時刻をずらす」設定を用意（見た目だけ変え、成長には影響させない）
- **季節**：現実の季節とは連動させない独自の周期。**現実の 1 か月 ＝ 1 季節**（春→夏→秋→冬で 4 か月）
  - **全世界共通の暦**：基準日（例：2027-01-01 UTC ＝ 春の始まり）からの経過月数で季節を決める。全プレイヤーが同時に同じ季節になる
    - 計算は端末の時刻だけで完結するので**サーバーは不要**
    - 季節の切り替えは UTC 基準の月初（日本時間では 1 日の 9:00）
    - 現実の季節と無関係なので、北半球・南半球の差も気にしなくてよい
  - 季節の切り替わりは数日かけて徐々に（葉の色、草の色、雪の積もり具合を連続的に変化）
  - 作物は季節ごとに育つ種類が変わる → 「次の季節が楽しみ」という通う動機になる
  - 全世界共通にする利点：「今は秋シーズン」という話題を共有できる、共有 URL で見た箱庭と自分の箱庭の季節がそろう、季節限定の花や生き物を全員同時に楽しめる、Web 版と Steam 版で同じ暦を使える
  - 注意点と対策

| 注意点 | 対策 |
|---|---|
| 始める時期によっては、最初が冬になる | 冬でも楽しめる要素（雪景色、冬の作物、冬鳥、温泉など）を用意する。最初の数日は「始まりの季節」として作物が育ちやすいボーナスを付ける |
| 季節限定のものを逃すと 4 か月待ち | 限定要素は見た目・図鑑中心にし、進行に必須なものにはしない |
| 端末の時刻を変えれば季節も変えられる | 1 人用の箱庭なので許容する（趣味寄りの方針と合う） |
- **成長時間は遊びやすさ優先で短縮**（目安。テストプレイで調整）

| 対象 | 成長時間（実時間） | 狙い |
|---|---|---|
| 葉物野菜 | 1〜2 時間 | 1 回のプレイ中に変化が見える |
| 穀物・根菜 | 4〜8 時間 | 朝植えて夜に収穫 |
| 果樹・樹木 | 1〜3 日 | 何日か通う楽しみ |
| 森の拡大・生態系 | 数日〜数週間 | 長期的な変化 |
- **シミュレーションはティック制**（例：1 ティック＝箱庭内 10 分）で決定論的に進める
- **オフライン進行**：保存時刻と再開時刻の差分から経過ティックを計算し、まとめて進める
  - 長時間放置は「要約シミュレーション」（個別ティックを回さず確率・期待値で一括計算）にして、起動を待たせない
  - 上限（例：最大 7 日分）を設けるとバランスが取りやすい

### 2.3 アクティビティ（干渉できるもの）
| カテゴリ | 例 | 放置での発展 |
|---|---|---|
| 農業 | 畑を耕す・種まき・水やり・収穫 | 成長段階が進む、水路の近くは早く育つ |
| 植林・森 | 苗木を植える、間伐 | 木が育ち、種を飛ばして森が広がる |
| 水 | 水路を掘る、ため池、堰 | 水が流れて湿地や草地ができる |
| 生き物 | 巣箱・池に魚を放す | 個体数が増減、生態系のバランス |
| 小さな住人 | 小屋を置くと住人が来る | 住人が勝手に畑仕事・釣りをする（眺める楽しさ） |
| 観察 | 写真モード、図鑑 | 珍しい生き物・花の出現で図鑑が埋まる |

### 2.3.1 住人（動物中心）
- 住人は**動物**（たぬき・うさぎ・きつね・くま・ねこ 等）。箱庭のサイズに合わせて数匹〜十数匹が暮らす
- 種類ごとに得意なことを持たせる（例：うさぎは畑仕事、くまは釣り、きつねは森の手入れ）→ どの動物を招くかで箱庭の発展の仕方が変わる
- 住人とは別に、野生の生き物（鳥・魚・蝶・鹿など）も箱庭を行き来する
- キャラクターデザインは独自のものにする（既存作品の住人に似せない）
- 現実時刻に合わせて動く：朝は畑へ、昼は釣りや散歩、夜は家に灯りがともり眠る
- 行動は「やりたいこと」の優先度で選ぶ簡単な仕組み（ユーティリティ AI）。経路探索はボクセル格子上の A*
- プレイヤーの干渉への反応：新しい畑を作ると世話をしに来る、水路ができると水遊びする 等
- 放置中は住人を個別に動かさず、「作業量」として成長計算にまとめて反映する（オフライン進行を軽くするため）
- 住人をクリックすると名前・好きなもの・最近の出来事が見られる（眺める楽しさ・愛着）

**見た目：ローポリ**
- 立方体の地形の上に、**フラットシェーディングのローポリ住人**を置く。地形と同じ色パレット・同じライティングを使い、世界観をそろえる
- 1 体あたり 300〜800 ポリゴン程度、テクスチャは使わず頂点カラー（またはパレット 1 枚）
- 制作：Blender でモデリング＋ボーン付け → glTF（.glb）で書き出し → three.js で読み込み
- アニメーション：歩く・しゃがむ（畑仕事）・釣る・座る・眠る・手を振る 等
  - 住人の動物は**二足歩行で体型（骨格）を共通化**し、頭・耳・しっぽの差し替えで種類を表現する → 全員で同じアニメーションを使い回せる
  - 四足歩行の野生動物は別の骨格で、動きも少なめ（歩く・止まる・食べる程度）にして工数を抑える
- 描画：人数が増えても重くならないよう、アニメーションをテクスチャに焼き込んで GPU インスタンシングで描く方式を検討
- 見た目のバリエーションは「色・帽子・持ち物」の組み合わせで出す（モデル数を増やさない）
- 同じくローポリで作るか検討：家・小物。地形と植物はボクセルのまま

**素材の調達（当面は CC0）**
- 自作するかは未定のため、まずは **CC0（権利表記不要・商用利用可）のローポリ素材**で作り、後から差し替えられるようにする
- 候補の入手先（いずれも使う前に素材ごとのライセンスを確認する）

| 入手先 | 内容 | 注意 |
|---|---|---|
| Quaternius | ローポリの動物・キャラクター・自然物。アニメーション付きの動物パックがある | CC0 |
| Kenney | 自然・家具・小物などのローポリ素材が豊富 | CC0 |
| Poly Pizza | 多数の作者のローポリ素材を検索できる | **CC0 と CC-BY が混在**。CC0 のものだけを使う |

- 使った素材は `assets/CREDITS.md` に「素材名・入手先 URL・ライセンス・入手日」を記録する（CC0 は表記不要だが、Steam 版で権利を確認できるようにするため）
- 複数の入手先の素材を混ぜると見た目がばらつくので、**同じ色パレットで塗り直す**（頂点カラーを読み込み時に置き換える）仕組みを用意する
- 二足歩行で骨格を共通化する方針は、素材の骨格がそろっていないと成り立たない。CC0 素材の段階では「素材についてきたアニメーションをそのまま使う」で割り切り、骨格の共通化は自作に切り替える時に行う

- 収穫物は「素材」として、新しい植物・装飾・地形ツールの解放に使う（緩やかな進行要素）
- **失敗やペナルティは控えめ**に（枯れても土に還る程度）。癒やしを優先

### 2.4 カメラ・操作
- 基本：斜め上 30〜45° の見下ろし、**水平方向に自由回転＋90°スナップ回転**ボタン
- 投影：低 FOV の透視投影（ミニチュア感と奥行きのバランスが良い）／正射影も切替候補
- ズーム：全景 ↔ 地面すれすれ（チルト角も連動して変化させると気持ちいい）
- 自動周回モード（スクリーンセーバー的にゆっくり回り続ける）
- 操作：マウス（ドラッグ回転・ホイールズーム・クリック干渉）
- スマホ（閲覧限定）：1 本指で回転、ピンチでズーム、写真撮影。編集 UI は出さない
  - 画質は自動で低〜中プリセット。PC で保存した箱庭をクラウドから読み込んで表示（オフライン進行も反映）
  - 閲覧限定なので、スマホ側からはクラウドへ書き戻さない（競合が起きない）

### 2.5 共有
- **段階 1：URL 共有**（サーバー不要）
  - 「シード＋差分」を圧縮して URL に埋め込む。開いた人は読み取り専用で眺められる
  - データが大きくて URL に収まらない場合は段階 2 へ
- **段階 2：共有ファイル**
  - Google Drive に「リンクを知っている人は閲覧可」のファイルとして書き出し、その ID を URL で渡す
- **段階 3（任意）：ギャラリー**
  - みんなの箱庭を一覧で見られる場所。ここだけは小さなサーバーが必要（後述の Render 無料枠を検討）
- 写真モードの画像は、端末に保存して SNS に投稿してもらう形が最も手軽

## 3. 技術構成

### 3.1 全体像
```
[ブラウザ]
 ├─ メインスレッド：描画（three.js WebGPURenderer）、UI、入力
 ├─ Web Worker：地形生成、メッシュ生成（Greedy Meshing）、シミュレーション
 ├─ IndexedDB / OPFS：ローカルの一次保存（オフライン・高速）
 └─ クラウドAPI（Google Drive 等）：ユーザー自身のストレージへ直接同期
[サーバー]
 └─ 静的ホスティングのみ（GitHub Pages / Cloudflare Pages 等、実質無料）
```

- 言語・ビルド：TypeScript ＋ Vite
- UI：軽量にするなら素の DOM / Preact、凝るなら React（three 部分は素の three.js 推奨）
- PWA 化：Service Worker でオフライン起動、ホーム画面追加

### 3.2 three.js の活用ポイント（先端技術）
| 技術 | 用途 |
|---|---|
| **WebGPURenderer** | 主要ブラウザで WebGPU が使える前提で採用。非対応環境は自動で WebGL2 にフォールバック |
| **TSL（Three Shading Language）** | シェーダーを JS/TS で記述。WebGPU/WebGL 両対応のマテリアルを一本化 |
| **Compute Shader（TSL compute）** | 草の揺れ・パーティクル（蛍、花びら、雨、雪）・水面の波計算を GPU で |
| **InstancedMesh / BatchedMesh** | 草・花・木の葉・小物を大量描画 |
| **ポストプロセス（TSL ノード）** | ティルトシフト DoF（ジオラマ感の決め手）、GTAO（ボクセルの隅の陰影）、Bloom、TRAA/SMAA、カラーグレーディング |
| **影** | 箱庭サイズなら単一の高解像度シャドウマップで十分。ソフトシャドウ（PCSS 風）で柔らかく |
| **大気・空** | 時間帯で変化する空（SkyMesh 系）、霧、ゴッドレイ |

### 3.3 水表現（本企画の見せ場）
ボクセル世界の水は「見た目」と「挙動」を分けて設計する。

**挙動（シミュレーション）**
- 水ボクセルのセルオートマトン（水量 0〜8 段階）で、掘った水路に水が流れ込む
- 流れの方向ベクトルをボクセルごとに持たせ、見た目（フローマップ）に渡す

**見た目（シェーダー）**
| 要素 | 手法 |
|---|---|
| 水面の波 | 小さな池・川：法線マップ 2 枚スクロール＋Gerstner 波。広い湖を作るなら Compute で FFT 波 |
| 流れ | フローマップ（流向に沿って法線・泡をスクロール）。滝は専用の縦スクロール＋飛沫パーティクル |
| 透明感・屈折 | シーンの深度・カラーを参照して屈折、**水深による色の吸収**（浅瀬は透明な水色→深いと濃紺） |
| 岸辺の泡 | 深度差から岸辺・岩まわりに泡ライン |
| 反射 | 空の環境マップ＋SSR（スクリーン空間反射）。見下ろし視点なので平面反射より SSR が相性良い |
| コースティクス | 水底に投影するアニメーションテクスチャ or 光線追跡風の計算 |
| インタラクション | クリックや魚・雨で波紋（波紋用のハイトマップを Compute で更新） |

> 見下ろし＋ミニチュアという条件では、「透明度・水深の色・コースティクス・岸の泡」が最も効果的。写実的な海洋 FFT は優先度を下げてよい。

### 3.4 パフォーマンス目標
- PC（内蔵 GPU）で 60fps、スマホで 30fps
- 品質プリセット（低／中／高）と、放置時の**省電力モード**（フレームレートを落とす、タブ非表示時は描画停止）
  - 「開きっぱなしで眺める」ゲームなので、発熱・バッテリー対策は重要

## 4. データ保存

### 4.1 データ規模の見積もり
| データ | 素朴な保存 | 工夫した保存 |
|---|---|---|
| ボクセル 64×64×32（約 13 万） | 1 byte/ボクセル ≒ 128 KB | パレット化＋RLE＋圧縮 → 数 KB〜20 KB |
| ボクセル 128×128×48（約 79 万） | ≒ 768 KB | → 20〜100 KB |
| 作物・樹木・生き物の状態 | JSON で数十〜数百 KB | バイナリ化で数十 KB |
| 写真モードのスクリーンショット | 1 枚 数百 KB〜数 MB | 別ファイル扱い（任意保存） |

**最も効く工夫：「シード＋差分」保存**
- 地形はシード値から毎回同じものを生成できるので、**プレイヤーが変えた部分だけ**を保存する
- 結果、セーブデータは通常 **数 KB〜数百 KB** に収まる見込み
- 圧縮はブラウザ標準の `CompressionStream('gzip')` で追加ライブラリ不要
- フォーマットにバージョン番号を必ず入れる（後で仕様変更しても移行できるように）

### 4.2 現行案（LocalStorage）の問題点
| 問題 | 内容 |
|---|---|
| 容量 | 1 オリジンあたり約 5 MB。文字列のみなのでバイナリは Base64 化で約 1.33 倍に膨らむ |
| **消える** | ブラウザのデータ削除、プライベートモード、容量逼迫時の削除。特に **Safari は一定期間（7 日）サイトを使わないとスクリプトで書いたストレージを消す**仕様があり、放置ゲームと相性が最悪 |
| 同期的 API | 大きいデータの書き込みでメインスレッドが固まる |
| 端末間共有不可 | PC とスマホで同じ箱庭を見られない |

→ **LocalStorage は設定値（画質など）だけに使い、セーブデータには使わない**。

### 4.3 推奨構成：ローカル＋クラウドの二層
```
① 一次保存：IndexedDB（または OPFS）
   - 数百 MB 以上使える、非同期、バイナリをそのまま保存
   - navigator.storage.persist() で「永続化」を要求し、自動削除されにくくする
   - オートセーブは頻繁に（例：1 分ごと・タブを閉じる時）
② 二次保存：ユーザーのクラウドストレージ（任意でログイン）
   - 数分おき／終了時／手動でアップロード
   - 起動時にクラウド側が新しければダウンロード（更新日時＋端末IDで競合判定）
③ 最終手段：ファイルとしてエクスポート／インポート
   - 認証不要。どのブラウザでも動く保険
```

### 4.4 Google Drive 直接連携の評価
**やり方**
- Google Identity Services（GIS）のトークンモデルで、ブラウザから直接アクセストークンを取得
- スコープは **`drive.appdata`**（アプリ専用の隠しフォルダ。ユーザーの他のファイルは見えない／触れない）
  - ユーザーにとって安心感があり、Google の審査も比較的軽い部類（公開前に最新の区分を要確認）
- Drive API v3 に `fetch` で直接アップロード／ダウンロード

**問題点・注意点**
| 問題 | 内容と対策 |
|---|---|
| トークンが約 1 時間で切れる | ブラウザ単体ではリフレッシュトークンを安全に持てない。期限切れ時に再取得（多くはワンクリック、場合によりポップアップ）。**同期を「節目だけ」にする**設計で体験を損ねにくくする |
| ポップアップ／サードパーティ Cookie 制限 | ブラウザの制限強化で無言の再認証が通らないことがある。ユーザー操作（ボタン押下）を起点に認証する |
| OAuth 同意画面の公開手続き | テスト中は 100 人までのテストユーザー制限。一般公開には同意画面の公開（スコープによっては審査）、プライバシーポリシー・ドメイン確認が必要 |
| 競合 | 2 端末で同時に遊ぶと上書きの恐れ。更新日時・世代番号で判定し、衝突時は「どちらを残すか」をユーザーに選ばせる |
| Google アカウント前提 | 持っていない／使いたくない人向けにエクスポートと他サービスを用意 |

**総評**：データ規模（数百 KB 程度）に対して Drive の `appDataFolder` は十分で、サーバー不要・保存コストゼロという目的に合っている。**ただし「メイン保存」ではなく「バックアップ兼端末間同期」と位置づけ、一次保存は IndexedDB に置く**のが安全。

### 4.5 その他の選択肢
| 方法 | サーバー | 特徴 | 向き不向き |
|---|---|---|---|
| **Dropbox API** | 不要 | ブラウザ向け PKCE フローでリフレッシュトークンが使え、**再ログインの手間が少ない**。アプリ専用フォルダあり | Drive の代替・併用として有力 |
| **OneDrive（MSAL.js）** | 不要 | SPA 向けに対応。リフレッシュトークンは 24 時間で失効 | Microsoft ユーザー向けに併用 |
| **File System Access API** | 不要 | ユーザーが選んだローカルフォルダに直接保存。そのフォルダを Drive/iCloud/Dropbox の同期フォルダにすれば実質クラウド同期 | Chromium 系 PC のみ。上級者向けオプション |
| **ファイルのエクスポート／インポート** | 不要 | 最も確実、どこでも動く | 必須の保険として実装 |
| **BaaS（Firebase / Supabase 等）** | マネージド | 認証・同期が楽、無料枠あり。ただし「自前サーバー負担ゼロ」の方針からは外れ、規模拡大で費用発生 | 将来、共有・ランキング等が欲しくなったら |
| **共有用 URL（データを URL に埋め込む）** | 不要 | シード＋差分が小さければ箱庭を URL で共有できる | 「見せ合う」機能として面白い |

**推奨**：IndexedDB（一次）＋ Google Drive（同期）＋ ファイルエクスポート（保険）。余力があれば Dropbox を追加。

## 5. マネタイズ

サーバーを持たない＝購入確認（課金の検証）を自前でやりにくい点が制約になる。それを踏まえた選択肢：

| 方式 | 内容 | 相性 | 備考 |
|---|---|---|---|
| **ブラウザゲームポータル** | CrazyGames / Poki 等に掲載し、広告収益を分配 | ◎ | 集客も得られる。各ポータルの SDK 組込みが必要。眺め系なので広告は「報酬型（見たら素材2倍）」中心に |
| **買い切り版（デスクトップ）** | Tauri / Electron でパッケージ化し Steam・itch.io で販売 | ◎ | 「開きっぱなしで眺める」需要は Steam の放置・デスクトップ常駐系と相性が良い。Web 版は体験版の位置づけに |
| **応援・サポーター** | Ko-fi / pixivFANBOX / Patreon、支援者の名前を箱庭の看板に | ○ | 早期から始めやすい。開発ログ発信とセット |
| **コスメ／拡張パック** | 新バイオーム（雪原・砂漠・南国）、生き物、装飾、季節イベント | ○ | Web だけで売るなら Gumroad / Lemon Squeezy のライセンスキー方式（多少の不正は許容する割り切り） |
| **壁紙・スクリーンセーバー版** | Wallpaper Engine 対応、自動周回モード | ○ | 眺める体験そのものが商品になる |
| 月額サブスク | クラウド同期などを有料化 | △ | 保存先はユーザーの Drive なので運営コストがかからず、課金の根拠が弱い |
| ガチャ | — | × | 癒やし系の世界観と合わない。避けるのが無難 |

**推奨ロードマップ**：①Web 版無料公開（＋支援窓口）で反応を見る → ②ポータル掲載で収益と集客 → ③拡張要素を足した買い切りデスクトップ版を Steam で。

### 5.1 方針（v0.2：趣味・ポートフォリオ寄り）
- Web 版は**無料で全機能（箱庭 1 つ）**を遊べる。広告は入れない（ポートフォリオとしての印象を優先）
- 支援窓口（Ko-fi / pixivFANBOX 等）を用意する
- **「複数の箱庭」は有料要素**。実現方法の候補：

| 方法 | 内容 | サーバー | 評価 |
|---|---|---|---|
| A. Steam 版の特典 | Steam 版（有料）では箱庭を複数持てる。Web 版は 1 つ | 不要 | ◎ 不正対策を Steam に任せられる。最もきれい |
| B. 支援者キー | 支援してくれた人に解放コードを配る。コードの検証はクライアント側のみ | 不要 | ○ 破ろうと思えば破れるが、趣味寄りなら許容できる |
| C. ライセンスキーの検証 | Gumroad / Lemon Squeezy の購入キーを、小さなサーバー経由で確認 | 少し必要 | △ Render の無料枠で可能だが、手間の割に得るものが少ない |

→ 当面は **B（支援者向け）**、Steam 版の発売後は **A** を主軸にする。

### 5.2 「ブラウザ無料＋Steam 有料」の前例
ブラウザで無料公開しつつ、Steam で有料版を販売して成功した例は複数ある。

| 作品 | 形 |
|---|---|
| **Cookie Clicker** | ブラウザ版は今も無料。2021 年に Steam で有料版を発売し大ヒット。Steam 版は実績・クラウドセーブ・サウンドトラック・追加要素が付く |
| **Townscaper** | 作者が Web で無料のプロトタイプを公開 → 完成版を Steam 等で有料販売。**箱庭・眺める系で本企画に最も近い前例** |
| **A Dark Room** | ブラウザ版は無料のまま、Steam・スマホ版を有料で販売 |
| **Melvor Idle** | ブラウザで始まった放置ゲーム。Steam 版を有料で展開 |

共通点：**無料版で十分楽しめる → 気に入った人が「応援を兼ねて」有料版を買う**。有料版には「オフライン動作・実績・クラウドセーブ・デスクトップ常駐」など**デスクトップならではの価値**を足している。本企画では「複数の箱庭」「壁紙モード」「デスクトップに置いておける」が有料版の価値になる。

> Steam 版を出すには Steamworks の登録料（1 タイトル 100 米ドル、一定の売上で返金）が必要。Web 版の技術（three.js）は Electron / Tauri でそのままパッケージ化できる。ただし WebGPU の対応状況はパッケージ方法によって変わるので、出す段階で確認する。

### 5.2.1 Steam 版を見越した設計（v0.3：ある程度目標にする）
最初から以下を守っておけば、Web 版のコードをほぼそのまま Steam 版にできる。

| 項目 | 方針 |
|---|---|
| パッケージ方法 | **Electron を第一候補**。Chromium を同梱するので WebGPU の挙動がどの PC でも同じになり、Steamworks 連携（実績・クラウドセーブ）のライブラリも揃っている。Tauri は配布サイズが小さいが、OS ごとに中身のブラウザが違い WebGPU の挙動がばらつく |
| 保存 | 保存先を差し替えられる作りにする（「保存先」の共通インターフェースを用意し、IndexedDB／Google Drive／Steam クラウド／ローカルファイルを実装として切り替える）。セーブ形式は Web 版と共通にし、**Web 版のセーブを Steam 版に引き継げる**ようにする |
| ブラウザ依存の処理 | URL・ブラウザ固有の機能に頼る箇所は 1 か所にまとめる（Steam 版では URL 共有を「共有コードのコピー」に置き換える 等） |
| 画面・入力 | 解像度変更・フルスクリーン・ウィンドウ表示に対応。キーボード操作にも対応しておく（Steam Deck を狙うならゲームパッド対応も） |
| 素材の権利 | 3D モデル・音楽・効果音は**自作か、商用利用可（CC0 等）のもの**だけを使い、出典を一覧で管理する |
| 有料版の価値 | 複数の箱庭、壁紙モード（デスクトップの背景として表示）、Steam 実績、Steam クラウドセーブ、オフライン動作 |
| ストアの準備 | ストアページ用のスクリーンショット・動画を撮りやすいよう、写真モードとカメラの自動周回を早めに作る（宣伝素材にもなる） |

> 進め方：Web 版で反応を見ながら作り込み → Steam のストアページを早めに公開して「ウィッシュリスト」を集める → 発売。ウィッシュリスト数は発売時の露出に大きく影響するので、ストアページは発売の数か月前には出しておくのが定石。

### 5.3 公開先（ホスティング）
| 候補 | 内容 | 評価 |
|---|---|---|
| **Render（静的サイト）** | 静的サイトのホスティングは無料で、スリープもしない | ◎ 既にアカウントがあるならそのまま使える |
| Render（Web サービス無料枠） | 一定時間アクセスがないとスリープし、次の起動に時間がかかる。無料の DB には期限がある | △ ゲーム本体の配信には使わない。ギャラリー等の補助 API 用途なら可 |
| Cloudflare Pages / GitHub Pages | 静的ホスティング、無料、CDN が速い | ◎ Render と同等の選択肢 |
| itch.io | Web 版を埋め込み公開でき、インディーゲームの集客がある | ○ 本体とは別に「出張所」として併用すると良い |

→ **本体は Render の静的サイト（または Cloudflare Pages）で無料公開＋itch.io にも掲載**。Render の Web サービス枠は、将来ギャラリーやキー検証が必要になった時のために取っておく。
※ Google ログインに使う OAuth の設定には公開 URL（ドメイン）の登録が必要なので、公開先は P2（保存）に入る前に決める。

> 法務面：広告や課金を入れる場合、プライバシーポリシー、特定商取引法に基づく表記、（ポータルによっては）年齢層への配慮が必要。

## 7. リスク

| リスク | 対策 |
|---|---|
| WebGPU 非対応・低スペック端末 | WebGL2 フォールバック、品質プリセット、GPU 処理の CPU 代替経路 |
| 開きっぱなしでの発熱・電池消費 | 省電力モード、非表示タブで停止、放置中は低 fps |
| オフライン進行の計算が重い | 要約シミュレーション、上限日数 |
| セーブデータ消失 | 二層保存＋エクスポート、セーブのバージョン管理と自動バックアップ世代 |
| OAuth 公開手続きの手間 | 早めに同意画面を設定、初期はエクスポートのみでもリリース可能にする |
| 表現の作り込みが際限なく膨らむ | P1 で「最低限の美しさ」の基準を決め、水以外は割り切る |
